## S3: per-user Gmail send

### Platform facts (evidence)
- Curated connector `google_workspace` (id `99cbe49f-…`) supports `per_user` and `service_account` and uses `managed_oauth`. Its Gmail actions include `google_workspace_gmail_message_send`, `google_workspace_gmail_draft_create`, `google_workspace_gmail_draft_send` and `google_workspace_gmail_message_reply`. `google_workspace_gmail_message_send` is a write action and needs scope `gmail.send`. Its input is `{to: string[] (email, min 1), subject, body, cc?, bcc?, html?, attachments?[{filename,mimeType,contentBase64}] (≤10, ≤64 KB total)}`. It has `service_credentials_supported: true`.
- For **Outlook** (P1), the path is the curated `microsoft_graph` connector (Microsoft 365). It also supports per-user.
- Docs: [Integration Hub](https://docs.wonderful.ai/build/tools/integration-hub):
  > "Use a service-account connection for a standalone or scheduled function. A per-user connection needs a supported conversation identity so Wonderful can determine whose authorization to use."

  > "Functions call actions explicitly in their code and do not need attached integration grants. The connection's Permissions tab controls which actions they can use." Use `context.integrations.call(connection, action, args)`.
- `@wonderful/types` `Integrations.call` JSDoc: "inside a conversation that is what the agent was attached; in a standalone or cron function it is what the function declares."
- `FunctionContext.metadata.user` is "Set for API Function invocations made with a session or user-scoped API key; UNDEFINED for cron / scheduled runs, public app session-token calls, admin-API-key calls, external-entity calls, and agent tools".
- `context.outbound` / `context.attachments` / `context.session` exist only on `ToolContextLibrary` (agent tools), not on `FunctionContext`. `context.email` exists in both. It sends through the agent's connected email channel (Gmail/Outlook/SMTP) or the default provider ([docs](https://docs.wonderful.ai/developer_platform/environment/builtins/email)).

### Exact calls and real output
```

→ {"connection_id":"3e6f759e-…","authorize_url":""}      # per-user: no admin consent; each person connects themselves

wful call post /api/v1/functions/merc-spike-gmail-send --data '{"mode":"send","conn":0}'
→ {"caller":{"email":"stefanos.k@wonderful.ai","id":"d2835589-…"},"connection":"merc-spike-gmail-peruser-send",
   "error":"Error: execute action: this integration needs you to connect your own account before it can act for you

This is the key result. The Function was called with my user-scoped CLI credential. The Hub did not refuse with "no conversation identity". It resolved the caller (`stefanos.k@wonderful.ai`) and asked *that person* to connect. So per-user resolution in a Function works off `metadata.user`. Once the person has connected, the same call should send. This must be confirmed after H1.

await context.integrations.call("merc-spike-gmail-peruser-send", "google_workspace_gmail_message_send", {

```

### What does NOT work, or is risky
- **A procedure step or cron as the sender.** `message-dispatch` (procedure, webhook trigger) → `message-send` has no `metadata.user`. Per-user resolution then has no identity. The docs state this explicitly. I did not run a procedure, so this rests on the docs, not on a proof.
- **The CLI cannot fix an allow-list after creation.** A connection created without `--actions` is unusable until someone edits Permissions in the Hub UI.
- **A per-user connection has `agent_automatic_access=true`** by default. This is fine for dev. In the demo workspace, restrict it to merc-buddy only.

### Recommendation (OPEN-03)
1. **Primary path.** `message-send` must run **in the rep's identity**:
   - **(a) App path.** The Rep App calls `approval-resolve` → `message-send` synchronously, with the rep's app session. `metadata.user` is then the rep, and the Hub uses the rep's Gmail.
   - **(b) Buddy path.** The `resolve_approval` buddy tool runs in the rep's conversation, which is a supported conversation identity. The tool can call the Hub action directly: attach `google_workspace_gmail_message_send` to merc-buddy as an integration tool, or call it in tool code with `context.integrations.call`.

   Either way, an idempotency guard on `approval_id` stays in `message-send`: check `message_approval.status` before sending, and write `sent` plus `external_message_id` after.
2. **Keep the `message-dispatch` procedure only for retries and status bookkeeping**, or drop it. It cannot be the sender for per-user Gmail.
3. **Fallback A.** A service-account Google Workspace connection with **service credentials** (Workspace domain-wide delegation). The connector supports `service_credentials` for `gmail_message_send`. This needs a Google Workspace admin. It is not possible with plain @gmail.com accounts.
4. **Fallback B (spec default).** `context.email.send` from a Function, through the agent's connected email channel or the default provider. Set the rep's address in the body and signature. This breaks "sent from the rep's own account". Use it for the demo only.

### Impact on OPEN items / contracts
- OPEN-03: **resolved in principle**: per-user works from a Function called by the rep's identity, not from a procedure. Confirm one real send after H1.
- `contracts/functions/message-send.json`: `callers: ["procedure"]` should become `["app","buddy"]`, and the gate should be the approval owner. See contract_changes.

## S4: offline audio transcription

### What works (real proof)
Function `POST merc-spike-transcribe` (id `dab74083-6cc7-480b-aff8-08fef0a0e0ef`). Body `{audio_base64, audio_mime}`. It calls:
```ts
const model = new LangChainGoogleGenAI.ChatGoogleGenerativeAI({ model: "gemini-2.5-flash", temperature: 0 });
await model.invoke([new LangChainCore.HumanMessage({ content: [
  { type: "text", text: "Transcribe this audio recording verbatim in its original language (likely Greek). Return only the transcript text." },
  { type: "media", mimeType: "audio/mp4", data: "<base64>" },
]})]);
```
The registry adapter (`registry-chat-model.js` `contentParts`) accepts `{type:"media"|"file", mimeType|mime_type, data}` base64 parts. External URLs are rejected.

| Clip | Format | Size | Model latency | Transcript (excerpt) |
|---|---|---|---|---|
| 8 s Greek (macOS `say -v Melina`) | m4a/AAC | 30 KB | 1.9 s | "Καλημέρα. Ήμουν στο καφέ Αύρα. Ο κύριος Νίκος θέλει 12 κιλά καφέ και δείγματα την Πέμπτη." |
| same | ogg/opus 24k | 19 KB | 1.8 s | identical meaning |
| same | webm/opus 24k | 21 KB | 3.0 s | "…καφέ Άβρα… 12 kg καφέ…" |
| same | wav 16k mono | 200 KB | 1.6 s | identical meaning |
| **39 s Greek debrief** | m4a/AAC 32k | 166 KB | **2.1 s** | full text correct except proper nouns: "Άβρα"→"Άδρα", "Aroma"→"Roma" |

The whole call took about 2.5 s end to end. That leaves plenty of room in REQ-DEB-002's 20 s budget. At 32 kbps AAC/opus, a 1 MB body (≈750 KB of audio after base64) holds about 3 minutes. 24 kbps opus is about 4 minutes.

### Caveats
- **No Model Profile.** `wful model-profiles create` returned **HTTP 500** three times (twice inline JSON, once from a file, with gemini-3.5-flash / gemini-2.5-flash endpoints). The proof uses the deprecated-but-supported `LangChainGoogleGenAI` compatibility constructor. Built-in gemini profiles (`meeting-summary`, `conversation-summary`, `attachment-ocr`) have `allowed_components` restrictions, so they are not for our use. Human step H3 covers creating the profile.
- **Proper nouns.** Put the rep's account names, contact names, competitor names and product names into the prompt as a vocabulary hint. Better still, let `debrief-process` resolve entities against tables. This drives REQ-DEB-004 evidence matching: the substring check runs against the transcript, so a mis-heard name breaks the evidence.
- **TTS test audio.** The clips are synthetic TTS, not real field audio with noise. Re-test with one real phone recording (H4).
- Other paths I looked at: the attachments pipeline batch transcription (AAC/AMR/MP3/MP4/OGG). It applies only to conversation or backoffice-task attachments (`context.attachments`, tools only) and is asynchronous. It is not needed. A container STT is not needed either.

### Recommendation (OPEN-04)
`voice-log-upload` has two parts. It stores `voice_log` (status `transcribing`), then transcribes inline in the same Function call with the inline-audio LLM: profile `merc-transcribe` once created, otherwise the `gemini-2.5-flash` compatibility alias. Then it calls `debrief-process`. App recording: `MediaRecorder` with `audio/webm;codecs=opus` (or `audio/mp4` on iOS Safari) at 24–32 kbps. Cap the length at about 3 min to stay under 1 MB. Remove the "container STT" fallback from the plan.
