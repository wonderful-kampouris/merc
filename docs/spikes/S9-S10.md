## 1. Wonderful Tables: exact payload (POST /api/v1/custom-tables)

Verified with `wful tables create --data-file`. The swagger definition is `shared_types.CreateCustomTableRequest`.

```json
{"name":"merc_spike_child","schema":"merc_spike","description":"...",
 "columns":[
  {"name":"id","type":"auto_uuid","required":true,"primary_key":true},
  {"name":"parent_id","type":"auto_uuid","required":true,
   "reference":{"table":"merc_spike.merc_spike_parent","on_delete":"restrict"}},
  {"name":"note","type":"string"},{"name":"amount_minor","type":"number"},
  {"name":"happened_at","type":"datetime"}],
 "indexes":[
  {"name":"merc_spike_child_parent_id_idx","columns":["parent_id"]},
  {"name":"merc_spike_child_parent_note_uq","columns":["parent_id","note"],"unique":true,"type":"btree"}]}
```

Required `build.py` `table_payload()` corrections (writers only, sources unchanged):

| Current writer output | Correct | Proof |
|---|---|---|
| top-level `"primary_key": ["id"]` | per column `"primary_key": true` (the field is not in the request schema) | swagger `models.CustomTableColumn.primary_key: boolean` |
| `"references": {"table","column","on_delete"}` | `"reference": {"table": "<schema>.<table>", "on_delete"}`. There is no `column`: a FK always targets the PK. **The table must be schema-qualified** (`merc.account`) | bare/unqualified ref → `400 references unknown table` |
| index `"method": "btree"/"gin"` | index `"type": "btree"/"gin"` (`unique` only on btree) | swagger `models.CustomTableIndex` |
| `"schema": "merc"` | correct as is. **The docs say `folder`, but that field is silently ignored** and the table lands at root | 1st attempt with `folder` → table created at root, FK lookup 400 |
| auto-generated `id` column | add `"primary_key": true` to it | |

Other facts:
- FK column type must equal the referenced PK type (`auto_uuid` → `auto_uuid`), as the contracts already do.
- Types: `string, number, boolean, date, datetime, enum, vector, big_vector, raw_vector, auto_inc_id, auto_uuid`. `enum` needs `enum_values: [...]`, so the writer *could* emit native enums from `x.enums`. Optional, but it gets DB-level enum checks for free.
- Columns also accept `default_value`. Index names max 49 chars (the writer truncates to 63, so **cut to 49**). Max 8 columns per index, 10 indexes, 50 columns.
- The create response echoes `reference` **without** `on_delete` when it is `restrict` (the default).
- Rows: `POST /custom-tables/{schema.table}/rows {"data":{...}}`. The response is `{id, data, created_at, updated_at}` with epoch-ms timestamps. A `datetime` with `+02:00` is stored and read back as UTC `Z`.
- Errors seen:
  - Bad FK → **400** `column 'parent_id' must reference an existing row in 'merc_spike.merc_spike_parent'`.
  - Deleting a referenced parent (restrict) → **400** `rows in another table still reference it`.
  - **Unique violation (single and composite) → 500 Internal server error**, not 409. The shared lib must pre-check natural keys, or map that 500 on a unique-indexed insert to `Error{code:"conflict"}` (409), to satisfy REQ-CORE-008.

Lifecycle run: created `merc_spike.merc_spike_parent` (id edc6bef8-…) and `merc_spike.merc_spike_child` (id d044ba52-…), inserted, tested, then **deleted both**. `tables list` shows no `merc_spike` tables left. A first mistaken root `merc_spike_parent` (created via the ignored `folder` field) was also deleted.

## 2. Functions: nested bodies and caller identity

Function `merc-spike-echo` (POST, shared workspace functions repo, `functions/merc-spike-echo/`, id 2110f810-…).
Call: `wful call post /api/v1/functions/merc-spike-echo --data-file fn_calls/nested_body.json --raw`

Body:

```json
{"account_id":"…","lines":[{"sku":"FLR-25","qty":3,"unit_price_minor":1250},…],
 "meta":{"nested":{"deep":true}},"caller":{"user_id":"attacker-spoof","role":"admin"}}
```

Result (excerpt):

```json
"data_types":{"account_id":"string","caller":"object","lines":"array","meta":"object"},
"total_minor":4650,
"caller":{"source":"context.metadata.user","user_id":"d2835589-…","email":"stefanos.k@wonderful.ai","raw_keys":["email","id","role","tenantId"]},
"spoofed_caller_in_body":{"role":"admin","user_id":"attacker-spoof"},
"metadata_keys":["function_id","function_slug","headers","rawBody","tenantId","user","workspaceId",…]
```

- **OPEN-09 resolved: nested POST bodies work.** `param_mapping: {}` (no declared params) still passes the whole JSON body into `context.data` with types preserved. A JSON-encoded string is **not** auto-parsed (`"lines":"[…]"` stays a string), so do not use the string-param fallback.
- `context.metadata.rawBody` and `headers` are present (auth headers are stripped).
- **Identity (REQ-CORE-002):** the platform sets `context.metadata.user` for user-scoped calls. The typings (`@wonderful/types` 0.1.39 `ContextMetadata.user`) say it is **undefined** for cron, public, admin-API-key, external-entity and **agent tool** calls. For calls from a Wonderful App (`api.invokeFunction`) it also carries `appRole/appRoles/appPermissions/appGroupIds/appPermissionGrants`, and `context.metadata.appAuthorization` (`{id, appId, appRole?, …}`) is set. That object is also set for anonymous app sessions, with `id` empty. Use `allowsAppPermission()` / `filterAppPermissionResources()` from `@wonderful/types` for row scope. App permission gates run **before** the function.
  - `me()` must read `context.metadata.user.id` (the Wonderful user id) and map it to `app_user` via `wuid`. If it is absent → `forbidden`. Any `caller`/`user_id` in the body is ignored. The spoof test above shows the body value never reaches `metadata.user`.
- **Envelope:** `wful call … --raw` returned the bare result object, with **no `{result, logs}` wrapper**. The docs show the wrapper for plain HTTP, and `api.invokeFunction` unwraps it anyway. App code should use `invokeFunction` and not depend on the envelope. The contract README line should say "may be wrapped" until the App WP checks it with `api.fetch`.

## 3. OPEN-10: one shared library for functions AND tools (proven)

The workspace already has a **Shared Library** repo (`shared_lib.git`, main @ 801a1f5, layout `tools/ utils/ kbs/ diacritics/`, package `@wonderful/shared-lib`). I pushed branch **`merc-spike-core`** (commit `940309a`, not merged) with `utils/merc_spike_core.ts` (`sumLinesMinor`, `MERC_SPIKE_CORE_VERSION`).

| Consumer | How it imports | Result |
|---|---|---|
| V2 agent tool `merc-spike-tools/tools/merc_spike_whoami/index.ts` | `wful agents lib add` (adds submodule `shared_lib` + `"@wonderful/shared-lib":"file:./shared_lib"`), then `import … from "../../shared_lib/utils/merc_spike_core"` | push to branch `merc-spike-lib` **accepted** (the pre-receive hook builds every tool). `wful validate --remote` → `merc-spike-tools @ merc-spike-lib is valid (server-side validation passed)` |

| Function `merc-spike-libcheck` (POST, **dedicated repo** `functions/merc-spike-libcheck-post`, id ce0dd156-…) | `git submodule add <shared_lib.git URL> shared_lib`, pin `940309a`, `import … from "./shared_lib/utils/merc_spike_core"` | `wful call post /api/v1/functions/merc-spike-libcheck --data '{"lines":[…]}'` → `{"core":"merc-spike-core@1","total_minor":4650}` |

Also proven: a relative import between folders of the shared functions repo (`functions/_merc_spike_lib/core.ts` from `merc-spike-echo`) bundles fine. `build.mjs` also has first-class support for a repo-root `shared/` folder.

**Recommendation (REQ-CORE-004):** put `@merc/core` in the **workspace Shared Library under `utils/merc_core/`** (TypeScript, no Node built-ins, deps only from the npm registry).
- Agents attach it with `wful agents lib add`.
- Functions use **one dedicated functions repo** (or the default repo) with `shared_lib` as a git submodule at the repo root, imported relatively.
- Both pin a commit, so a lib change means: merge the shared_lib MR → bump the gitlink in the agent repo and the functions repo → push both. The deploy script should do this bump.
- Constraints:
  - Function `package.json` deps reject `file:`/`link:`, so the function side must use a **relative import, not `@wonderful/shared-lib`**.
  - The agent-side gitlink must be on shared_lib `main` before the agent is published. Remote validation passed on an unmerged commit here, but the skill docs say publish/merge rejects that.
  - The shared functions repo already holds other WPs' spike functions, so adding a root submodule there is a repo-wide change. Prefer one Merc functions repo owned by the shared-lib WP.
- **The HMAC fallback (`MERC_INTERNAL_CALL_KEY`) is not needed.**

## 4. OPEN-08 / REQ-BUD-002: rep identity inside a buddy tool

From `@wonderful/types` 0.1.39 `context.d.ts` and the docs (`builtins/metadata`, `chat-sdk/server-authentication`, `chat-sdk/guest-promotion`, `end-user-authentication`):

- `context.metadata.user` is **UNDEFINED for agent tools**, and `context.session.getUser()` "returns `null` for voice and chat sessions". So the Functions identity path does not exist in tools.
- A tool's handler has `ctx.metadata.{tenantId, workspaceId, contextId, contextType, communication.{id,type,metadata,…}, agent}`. `communication.metadata` is the only session channel.
- The Chat SDK supports **server authentication**:
  1. A backend with an API key (Chat/Create + Communications/View) calls `wonderful.auth.mintToken({user:{id}, metadata, expiresInSeconds})` (`@wonderful/node`).
  2. The browser gets only the short-lived signed JWT (`createChat({token:{token,expiresAt,refresh}})`). It works for browser voice, since the experience is chosen per embed.
  3. The platform derives the customer user from the token and stores it on the communication (`customer_user`). For promoted chats the documented metadata keys are `wonderful.customer_user.id` and `wonderful.web_sdk.entity_id`.
- **The docs warn these metadata values can be edited by authorized metadata writers and "metadata alone is not an immutable proof"**, and the JWT is signed but not encrypted.

**Recommendation:**
1. `fn:merc-chat-token` (POST, app-callable, gated) reads `context.metadata.user.id` (the trusted app caller), maps it to `app_user.id`, and mints a token with `user.id = "<app_user.id>"`.
   - **Option A (preferred):** call the mint endpoint over `fetch` with a secret `MERC_CHAT_API_KEY` (no npm dependency on `@wonderful/node`, which must be confirmed in the function build).
   - Also put `metadata.merc_sig = HMAC(MERC_INTERNAL_CALL_KEY, app_user.id|org_id|exp)`.
2. Every buddy tool's `me()` reads `communication.metadata["wonderful.customer_user.id"]` (fallback `wonderful.web_sdk.entity_id`) **and** verifies the HMAC claim before it trusts it. The model never fills `caller`, so `caller` stays in `inject`.

This is the contracts' default (a "signed short-lived token in session metadata, verified by the tools") using platform-native token minting.

**Not runtime-verified here:** the exact metadata key a token-started *voice* session shows to a tool, and whether the token `metadata` claims are copied into `communication.metadata`. The spike tool `merc_spike_whoami` (branch `merc-spike-lib`) echoes all candidate sources (`metadata.user`, `session.getUser()`, `wonderful.customer_user.id`, `wonderful.web_sdk.auth_mode`, `contextId/Type`). Run it in the S1/S2 browser-voice proof, or from the Agent Studio tool Tests tab, to close this out.

## 5. Impact on contracts / build.py (change requests, not edits)

1. `build.py table_payload()`: the fixes in §1 (per-column `primary_key`, `reference{table:"merc.<t>",on_delete}`, index `type`, index-name ≤ 49). Optionally native `enum` + `enum_values`.
2. `contracts/README.md`:
   - "Unverified payload shapes": tables are now verified.
   - Functions envelope: "may be wrapped; app uses invokeFunction".
   - GET rule stays. Nested bodies are fine on POST.
3. Error mapping: unique violations come back as 500. The shared data layer must map them to `conflict` (409) or pre-check.
4. Function create metadata, for whoever writes the deploy step: `POST /api/v1/wonderful-functions` (`shared_types.CreateWonderfulFunctionRequest`) takes `{name, description, method, path_slug, param_mapping:{query_params,body_params}, timeout_ms, is_public, dependencies, files, repo_key, repo_path, dedicated_repo, service_account_id, allowed_ips}`. The git-backed `config.json` is `{"kind":"http","name","description","method","path_slug","param_mapping":{}}`. Declared `param_mapping` only supports scalar `string|number|boolean`, so leave it empty for nested bodies and validate them in code against the contract JSON schema. App-published APIs accept `input_schema`. A function only gets `context.api` when `service_account_id` is set (needed for `merc-live` pushes).
5. V2 tool format: `tools/<slug>/index.ts` with `w.tool({name, description, params: s.object({...}), handler(ctx, params)})`, attached through `skills/<skill>/skill.json` `tools` **map** keyed by name (`type`, `description`, `parameters[{name,type,required,is_exposed_to_llm}]`, `config`). Injected values (`caller`, `conversation_id`, `language`) are **not** params. They are read in the handler from `ctx.metadata`.
