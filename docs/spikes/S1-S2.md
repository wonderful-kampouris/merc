## Exact API calls that worked

```bash
W="wful --profile hackathon --workspace 7b52cbc0-4e7d-5fc4-a2df-a76f5ecae464"
# agent
$W agents create --slug merc-spike-voice --display-name "Merc Spike Voice" --mode conversational --voice athina_greek --dir spikes/s1-s2/agent --skip-install
# app (git-backed; push to main deploys)
$W apps create --name merc-spike-s1s2 --description "..."
$W apps clone --app merc-spike-s1s2 --dir spikes/s1-s2/app
git push   # then:
$W apps deployments --app merc-spike-s1s2 --wait --commit <sha>      # "succeeded, Live after 22.3s"
# Chat SDK key + allowed domains (endpoints are not in swagger; taken from the Agent Studio UI bundle)
$W call post /api/v1/web-chat/agents/<agent_id>/key --data '{"name":"merc-...","allowed_domains":["https://app.greece-hackathon.sb.wonderful.ai","https://default.app.greece-hackathon.sb.wonderful.ai"]}'
$W call patch /api/v1/web-chat/keys/<key_id> --data '{"require_captcha":false}'     # also takes allowed_domains, name, ...
$W call get   /api/v1/web-chat/keys
$W call get   /api/v1/web-chat/agents/<agent_id>/configs
$W call get   /api/v1/web-chat/sdk            # {"preferred_version":"0.7.50","resolved_version":"0.7.52"}
# anonymous access + share link
$W call put  /api/v2/apps/<app_id> --data '{"anonymous_access_enabled":true}'
$W call post /api/v2/apps/<app_id>/asset-session --data '{"expires_in":86400}'
```

Other endpoints seen in the UI bundle, not called: `PUT /web-chat/keys/{key}/agents/{agent}/config` (logo, appearance, `embed_preferences`), `POST /web-chat/keys/{key}/agents/{agent}/regenerate`, `DELETE /web-chat/keys/{key}/agents/{agent}/config`, `POST /web-chat/npm-token`.

Docs drift:
- The external-apps docs give `POST /api/v1/apps/:id/asset-session`, which returns **404**. The working path is `/api/v2/apps/:id/asset-session`.
- The swagger from `wful swagger get` has no `/web-chat/*` admin endpoints and no `/jwt/sign`.

## Widget code (what is in the App)

```ts
// load https://cdn.wonderful.ai/chat-sdk/latest/chat-sdk.min.js, then:
const config = { key: SDK_KEY, agentId: AGENT_ID, baseUrl: "https://default.api.greece-hackathon.sb.wonderful.ai",
                 modalities: ["voice"], title: "Merc voice test" };
await wonderful.preload(config);
const chat = wonderful.createChat(config, hostDivInsideTheApp);   // floating launcher + panel
chat.setState({ open: true });                                    // from our own "Open voice buddy" button
```

Observed in the browser (`evidence/browser-probe.json`):
- `POST /api/v1/web-chat/handshake` → 200
- `GET /api/v1/web-chat/config?agent_id=…` → 200
- `chat.connection.status()` → `"connected"`
- `chat.voice.getState()` → `{muted:false,status:"idle"}`
- Page facts: `inIframe:false`, `isSecureContext:true`, `featurePolicy.allowsFeature('microphone'):true`, `navigator.mediaDevices.getUserMedia` present.

Note: `chat.connection.status` and `.error` are signal **functions**, not values. Call them.

### Why the CDN and not the npm package

`pnpm add @wonderful/chat` fails on this computer with `ERR_PNPM_FETCH_401` from `https://default.api.greece-hackathon.sb.wonderful.ai/api/npm/`. This computer has no npm login for the hackathon registry (`npm view` works, pnpm install does not). The fix is a one-time interactive `npm login --auth-type=web --scope=@wonderful --registry=https://default.api.greece-hackathon.sb.wonderful.ai/api/npm/` (human step). The server-side App build has its own registry access, so after the login the package path should also work in the build. Not verified.

The CDN build works, but it only exposes the floating widget (`createChat` / `render` / `preload`), not `renderConversation`. For the production Rep app (WP that builds the buddy screen), prefer the npm package (`renderConversation` inline on the Today screen) once the registry login is done. Keep the CDN as the fallback.

## Bot protection (captcha)

The key is created with `require_captcha: true` by default. In the automated browser the handshake then returned **428** with `[Cloudflare Turnstile] Error: 600010`. After `PATCH … {"require_captcha":false}` the handshake returned 200. On a real phone Turnstile will probably pass invisibly, but this is unverified.

For the demo:
- either keep captcha off on the dev and demo keys (the origin allowlist still applies), or
- move to signed user tokens. Docs say allowed domains and bot protection do **not** apply to signed tokens.

## Mic permission behaviour

- The widget asks for the microphone **only when the user taps "Start a call"** (docs, and seen: no prompt before the tap).
- HTTPS is required. Both app origins are HTTPS.
- The App is mounted in a Shadow DOM (`attachShadow` in the host bundle), not an iframe. The host page sends `content-security-policy: frame-ancestors 'self'` and no `Permissions-Policy` header, and `featurePolicy.allowsFeature('microphone')` is true. So nothing in the platform blocks mic access.
- With the permission denied, tapping Start a call shows **"Microphone permission was denied"**, and no voice session is created (`evidence/s2-mic-denied-message.png`). The user must re-enable it in the browser's site settings.
- A full page reload or leaving the page ends the call. Client-side route changes keep it if the `chat` handle is kept above the routes (docs).

## Decision: internal vs external App (progress 0.8)

**Recommendation: internal (signed-in) App for both the Rep and the Management shells.** The demo keeps a pre-minted external link only as a fallback.

Why:
1. The app contract (`spec/contracts/app/app.json`) relies on app roles, permissions and relations. Those need a real user, and the external mode has none.
2. `me()` / REQ-BUD-002 identity: the internal app has `context.metadata.user.id` server-side in every Function. The external mode would need its own token scheme.
3. One origin and one key serve both. The SDK key allowlist covers both app hosts.
4. External share links cap at 24 h and expose only Functions. That is fine for a demo, wrong for daily use.

Remaining 0.2 uncertainty: Wonderful login on a real phone (SSO/MFA friction) and real-phone mic. Both are covered by the human step below.
