## S7: what was tested

### 1. Campaigns (the contracted path)
```
$ wful --profile hackathon --workspace 7b52cbc0-… campaigns list
error: campaigns list: request failed (403): campaigns is not installed for this tenant
```
The campaign API is also missing from the swagger: no `campaign` paths, only the `campaign-skill` repo paths. Documented API, for when an admin installs it:
```
wful campaigns create --name merc-manager-approvals --agent <merc-approver id> --timezone Europe/Athens \
     --from-number <E164 on an outbound trunk> --max-concurrent-calls 5 --max-total-attempts 1 --max-attempts-per-day 1 \
     --answer-timeout-after-progress-seconds 25
wful campaigns rule-replace <cid> --data-file rules.json      # no_answer/busy/voicemail/failed -> Stop(failure), answered -> Stop(success)
wful campaigns call-time-replace <cid> --data-file times.json # Mon-Sun 08:00-20:00 Europe/Athens (REQ-APV-003)
wful campaigns activate <cid>
wful campaigns consumer-create <cid> --name "Eleni" --external-id <approval_id> --phone <E164> \
     --consumer-data '{"approval_id":"…","requester":"Nikos"}'   # one consumer per request; the agent reads it via the Get Consumer Info tool
wful campaigns attempt-list <cid>   # outcomes: answered/no_answer/busy/voicemail/failed/invalid_number
```
From a Function, the same calls would go through `context.api`, but the REST paths are not in the swagger. They would have to be confirmed once campaigns are installed. Note that campaigns dial in cycles. A "ring in under 30 s" target (REQ-DSC-002) is not guaranteed by a dial cycle.

### 2. Single outbound call API (recommended replacement)
Swagger: `POST /api/v1/agents/outbound`, "Initiate outbound call", permission `agents:edit` (workspace).
```json
// shared_types.OutboundCallRequest
{ "from": "+30…", "to": "+30…", "call_purpose": "merc_approval:<approval_id>",
  "communication_id": "<optional>", "answer_timeout_after_progress_seconds": 25 }   // required: from, to, call_purpose
// responses: 200 {…} | 400 invalid | 502 provider could not initiate | 503 outbound telephony unavailable
```
According to the outbound SIP trunk docs, the **From number selects the outbound trunk**, and the agent that answers is the one the From number is attached to (Agent Studio → Channels → Phone Numbers). So `merc-approver` needs its own caller ID on an outbound trunk.

Dry-run evidence. A request without `to` cannot dial:
```
$ wful … call post /api/v1/agents/outbound --data '{"call_purpose":"merc_spike probe","from":"+12763303779"}'
error: (503): outbound_call_unavailable: Outbound calling is not configured for this number. Configure a telephony provider or outbound SIP trunk, then try again.
$ wful … call post /api/v1/agents/outbound --data '{}'
error: (502): Bad Gateway
```
From a Function (proof `merc-spike-outbound-probe`, POST, id `252adc25-c21c-4aae-9c9f-7baa147a491d`, draft run via `POST /api/v1/wonderful-functions/{id}/run`), with the payload `fn:discount-request` will send (minus `to`):
```
ctx.api.post /v1/agents/outbound {"from":"+12763303779","call_purpose":"merc_approval:…a1","answer_timeout_after_progress_seconds":25}
-> 400: context.api is not configured: set a service account on this function (or on the agent, for a tool) before calling the platform API
```
So the Function's `context.api` is wired to `https://platform.wonderful.internal/v1/agents/outbound`. The only thing missing is a service account: `PUT /api/v1/wonderful-functions/{id}` with `service_account_id`, or the function's Details → Service account.

### 4. Call metadata
- The single-call API has no metadata field. Carry `merc_approval:<approval_id>` in `call_purpose`. `communication_id` lets us pre-assign or know the conversation id; the semantics are undocumented.
- On the call, tools see `context.metadata.communication.{id,toNumber,fromNumber,direction}`. **Unverified:** whether `call_purpose` reaches `communication.metadata`. Fallback that always works: `get_approval_brief` resolves the approval from the newest `manager_call` row with `outcome in (queued, ringing)` for `callee.phone == context.metadata.communication.toNumber`, and stores `wonderful_conversation_id`.
- With campaigns, the consumer's `external_id` and `consumer_data` carry it, read through the built-in Get Consumer Info tool.

### 5. Outcome hook (feeds `fn:manager-call-outcome`, REQ-DSC-006)
| Outcome | How we learn it without campaigns |
|---|---|
| answered + decided | `record_approval_decision` tool → `fn:approval-decide` |
| voicemail | Tool with trigger `OnVoicemailDetected` (docs: voice-and-language/voicemail-detection). It speaks the safe voicemail line (REQ-DSC-008), then calls `report_call_outcome(voicemail)`. |
| answered, no decision / hang-up | Tool with trigger `OnEnd` (present in `@wonderful/types`) → `report_call_outcome(failed)` if no decision was recorded |
| no_answer / busy / failed | No agent session starts, so no trigger fires. Set `answer_timeout_after_progress_seconds: 25`, and add a **lazy timeout**: `approval-status` (polled by the buddy) and `approval-sla-watch` mark `manager_call` `no_answer` when `started_at + 45 s` passes with no `answered`. Then they run the async fallback. A 502/503 from `/agents/outbound` maps to `failed` and goes async at once. |

## S8: relaying the decision into the live buddy conversation
| Option | How | Pros | Cons | Verdict |
|---|---|---|---|---|
| A. Polling tool | `get_approval_status(approval_id)` → `fn:approval-status`. The buddy skill says "check again when the rep asks or after the next turn". | Already in contracts. No platform risk. Works offline-tolerant. | The rep hears it only when the buddy checks. That needs a turn. | **Baseline (must have)** |
| B. External event injection | Function `approval-decide` → `context.api.post('/v1/communications/{buddy_comm_id}/external-events', {event_id: 'approval:'+id, type:'merc.approval.decided', message:'Eleni offered 6%', trigger_turn:true, interrupt_current_turn:false})`. Permission `communications:edit`. | The buddy speaks the decision unprompted ("Eleni offered 6%"). Idempotent `event_id`. | Needs the buddy conversation id stored on the approval, and a service account. Not verified on a live Chat SDK voice session. | **Recommended upgrade** |
| C. Hold / wait inside a tool | The tool blocks with `startHold('hold')` while polling the table | Single turn | The tool and function timeout is 30 s, and a manager call takes longer. It blocks the rep's conversation with Miltos. It needs a recording clip. | Reject |
| D. Push + SMS | merc-live push (`context.api.post('/v1/function-sockets/messages')`, needs a service account) + `context.telephony.sendSms` | Works when the buddy session has ended | **SMS:** no tenant number is SMS-capable (`sms_capability:false` on all 8). Platform default sender resolution is unverified and was not tested (no real SMS). | Push = yes (fallback). SMS = blocked until an SMS sender exists. |

Proof for B, endpoint reachability (CLI, fake id, nothing delivered):
```
$ wful … call post /api/v1/communications/00000000-…/external-events --data '{"event_id":"merc_spike_probe_1","type":"merc.approval.decided","message":"probe","trigger_turn":false}'
error: (404): communication not found: record not found
```
The schema (`components_communications_api.createExternalEventRequest`) is: `event_id, type, message, metadata, trigger_turn, interrupt_current_turn`.

**Recommendation:** A + B + push. Store `buddy_conversation_id` (from `context.metadata.communication.id`, injected into `request_manager_approval`) on the approval. `approval-decide` fires the external event and the merc-live push. The buddy also polls with A, so the decision still reaches the rep if B fails.

## Recommendation for the build
1. Replace "campaign consumer per request" with **one `POST /v1/agents/outbound` per request** from `fn:discount-request`: `from` = merc-approver caller ID, `to` = approver phone, `call_purpose` = `merc_approval:<approval_id>`, timeout 25 s. Keep campaigns as a later option if they get installed. With campaigns, the "ring in under 30 s" target depends on the dial cycle.
2. Check call hours (08:00 to 20:00 org timezone, REQ-APV-003) in `fn:discount-request` itself. Without campaigns there are no platform call-time windows.
3. If there is no outbound number or service account, or the call returns 502/503, go straight to async (REQ-DSC-006). This is also the OPEN-07 fallback, so the build works end-to-end before the telephony is set up.
4. `merc-approver` tools: `report_call_outcome` is triggered by `OnVoicemailDetected` and `OnEnd`, plus the lazy timeout above.
